Module-only, default-off proposal: `BIZTANIA_DYNAMIC_ARTIFACTS=off|on`. This flag is not wired. No storage adapter, migration, delivery, service hook or durable runtime claim is included.

For follow-ups load the exact protected conversation evidence/query/claim refs, not `lastScope` or current dashboard evidence. Wave 1 rejects `requestedUses: artifact`; convert its already accepted **answer** evidence, or coordinate the Wave 2 capability contract. Never fall back to a broader legacy query when preparation is rejected.
- Resolve a current server catalog, actor and exact authorized `ArtifactStore.latest(artifactId)` result first. Lookup failure is an error, never `absent`. Provide fresh `ActorAuthority` and verified Wave 1 `EvidenceBundle`/`ClaimGraph` objects to `createArtifactResponse(graph)` then `prepareArtifact(PrepareArtifactInput): PrepareArtifactResult`. AI emits `artifactPlanSchema` only; server supplies artifact identity, time, authority, latest state and evidence. The response adapter implements the existing required ResponsePlan family with deterministic, complete claim/citation binding; no nullable response ref or model-authored factual prose. Wire Wave 2's richer response family only after a reviewed adapter preserves those bindings.
- `prepareInTransaction` (`dashboard_create`, around line 631) and `revisePendingActionInTransaction` (around line 680): register a separate artifact binding under the artifacts flag. Preserve existing dashboard semantics and approval rules. Revisions require an exact base ref, the same owner/query/evidence/claims/response refs, and append a new version; changed query scope/data requires a new artifact. Do not translate an artifact rejection into `dashboard_create` or a template.
- On user confirmation inside the effect transaction: reload actor, latest artifact ref and current catalog policy; `prepareArtifactWrite({preview, confirmedPreview, latestRef, authority, now})` returns `{record, expectedLatest}` only. Apply `ArtifactStore.append` atomically against the exact expectation; `null` means confirmed absent. Uniqueness must protect `(artifactId, revision)` and CAS must protect the latest pointer. Retain old versions append-only. Concurrent/replayed writes return conflict. Permission and catalog checks must share the transaction boundary with append; the module cannot close a race after its pure function returns.
- After append: independently read the exact version and call `verifyArtifactWrite({write, readback, authority})`; only `status: verified` reports success. Do not pass an append acknowledgement as readback. On reload call `loadArtifact({record, expectedRef, authority})`, where record comes from the **server store** and expectedRef from **protected exact state**. Never expose this trusted-store hydration function to AI/browser JSON. The result becomes a runtime-trusted renderer/share input; arbitrary JSON records do not.
- `authorizeArtifactShare` accepts `artifactSharePlanSchema`, a runtime-trusted record, freshly loaded sender/recipient including exact role, and server-owned recipient/role-pair policy. Both identities must read the **whole** stored scope with every stored read permission; the sender must own it and have `dashboard.share`. It returns exact authorization refs/scope/policy digest with `confirmationRequired: true`, `executionAvailable: false`. Wave 4 owns fresh policy recheck, explicit consent/confirmation, expiry, channels, execution and verified receipt. Do not send or create URLs from this preview.

## Version/persistence boundaries

Strict immutable `ArtifactVersion` retains the complete original EvidenceBundle, ClaimGraph, QueryPlan and deterministic ResponsePlan, their refs/digests, source timestamps, coverage, limits and interpretation labels. A chart is a visual projection; the full selected claim table and original evidence population are retained, including top-N semantics and limitations. Titles are inert labels, not grounded narrative. CSV is an in-memory preview with formula-neutralized text cells; download/delivery is a separately confirmed effect owned by the lead.

`ArtifactStore` is an interface only. The lead must add an authorization-aware append-only transactional adapter and protected conversation artifact refs. Runtime-bound Wave 1 objects cannot be reconstructed by casting stored JSON; reexecute the exact query against an immutable evidence reader, or supply a reviewed Wave 2 evidence hydration boundary. A digest proves integrity against a trusted expected ref; it does not prove facts, authorization, freshness or store provenance on its own.

`ArtifactAuthority` extends Wave 1 authority with required `catalogDigest`, resolved from the **current server catalog**. Every preparation/read/render/share/write boundary fails closed if it differs from the record's pinned `catalogSnapshot`. Current policy or trust changes require replan; no historical minimum can silently preserve a revoked grant. The module checks this pin and actor scope/permissions; the current catalog lookup and transaction closure remain integration-owned.

## Live wiring (Track B lane C)

- Versions persist beside their chart expression (`visual` on the immutable version row); `GET /api/artifacts` lists history, `GET /api/artifacts/{id}?revision=` reloads one version under current authority, and the reload compiles to the identical spec as the preview.
- `artifact.share` (registered, confirm-tier) calls `authorizeArtifactShare` for the sender and each recipient at prepare, again at confirm and again inside the delivery transaction; recipients open a read-only view through their own inbox message (`GET /api/artifacts/shared/{messageId}`), which reauthorizes them for the whole scope on every open.
- Drilldown is `GET /api/artifacts/{id}/drilldown`: a linked read re-run through the registered query path under the viewer's current authority.
- Excel export: not offered. The plan promises CSV only (ArtifactPlan outputFormat preview|csv); the decision is recorded here.
